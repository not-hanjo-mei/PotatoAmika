# TTS 引擎阶段三报告：aarch64 移植、A57 正确性、内存收口、真机标定包

阶段二结束时宿主功能已完整（见 STAGE2.md），但只在 x86 上跑过，常驻 RSS 1.83 至 1.88 GB，离 300 MB 量级的驻留目标差着量级。阶段三做四件事：把宿主搬到 aarch64/musl 并链接系统 onnxruntime 1.24.4；在 A57 模拟环境里按阶段二同口径验正确性；把解码器权重改成打包形态驻留、压 RSS；备好真机标定包。前任执行者已完成输出链的软削波定版变更与 packed 的大部分实现，本阶段先盘点再续做。

## 一、盘点结论

接手时在途产物已成形，不是半成品框架：

- `packed.h`（25.8 KB）已实现打包驻留与融合反量化：自定义算子 `potato::PackedMatMul`（W4/W8 的 MatMul 与 transB Gemm 共四种模式）、跨两张解码图按内容去重的权重池 WeightPool、标量版融合反量化 GEMV/GEMM 内核加小线程池。
- `packed_graphs/` 已生成：两张解码图改写为打包输入形态（fp32 图本体各约 3.16 MB），每图带一份 sidecar JSON 列明打包张量；生成器是 `make_packed_graphs.py`。
- `main.cpp` 已接 `--packed`（仅 W4；W8 保持烘焙路径）、`--no-arena`、`--opt-level` 开关；`tf_check.cpp` 已支持 `--mode baked|packed` 与 `--ref/--dump` 逐歩 logits 比对；`kbench.cpp` 是内核隔离微基准。`build/` 里四个二进制（tts_host、tf_check、kbench、test_softclip）均已编好，软削波已在其中。
- 阶段二的验证日志、参考包、词典、烘焙图（emit_w4）都在。

也就是说内存收口的主体设计与实现是前任完成的；本阶段把它跑通、逐台阶量 RSS，并完成移植、A57 验证与标定包。软削波按要求未重做，只复核。

## 二、内存收口

### 机制

- 打包驻留：解码器权重以 W4 打包字节原样驻留（分组 64 不对称，含 scale 与 zero），不再在启动时反量化烘焙成 fp32。权重池按张量内容去重：初代 W4 包下两张解码图的张量逐字节相同，只存一份（逻辑量 88,347,648 B，实际唯一 44,173,824 B）；W4-plus 换代后改为每图一个池，去重基本失效（见第八节），台阶账的落点不变。
- 融合反量化：自定义算子在 MatMul/Gemm 计算时逐块反量化权重，激活全程 fp32（与定版口径一致：这颗芯片无点积指令，int8 计算是负收益；A16 在此实际为 fp32 计算）。
- 关 ORT 的 CPU 内存池（`--no-arena`）：ORT 默认把中间缓冲留在池里复用，烘焙模式下这一项单独占约 760 MB。

### RSS 台阶账（x86，每档一个贪心 S0 请求后取宿主自报 RSS）

1. 阶段二基线，烘焙加 arena 开：1,837.82 MB（启动后 1,779 MB），与 STAGE2.md 的 1.83 至 1.88 GB 对上。
2. 烘焙加关 arena：1,077.36 MB。arena 一项约 760 MB。
3. 打包加 arena 开：677.44 MB（启动后 632 MB）。
4. 打包加关 arena：518.48 MB（启动后 434 MB）。
5. 打包加关 arena 加图优化等级 basic，连跑 S0/S1/S2 三句：513.70、465.25、491.34 MB，稳态在 465 至 518 MB 之间浮动（随单句的工作区与 KV 涨落）；优化等级对 RSS 无实质影响。
6. 纯解码侧的对照（tf_check 进程，两档同含编码器、无 vits，差异只在解码器侧）：烘焙 1,277 MB，打包 262 至 275 MB，解码侧单独省下约 1.0 GB。

每档的数值等价都验过：打包模式教师强迫一致率 299/361，与烘焙逐歩 argmax 361/361 相同，logits 最大差 8.01e-05（浮点累加顺序噪声量级）。打包不是近似替代，是同一计算换了权重供给方式。

注：这一节的台阶账用的是初代 W4 包。GPT 包已换代为 W4-plus（见第八节），新包同体积，复测的落点不变：tf_check 打包进程 304.6 MB（初代 262 至 275，差值来自权重池去重失效，见第八节），宿主打包加关 arena 单句 504.66 MB，仍在第 4、5 档的带内。

### 离 300 MB 还差什么

稳态 465 至 518 MB 里最大的一块是 vits：它的权重仍走烘焙路径，E 混合包在加载时反量化注入 248,561,536 B 的 fp32 权重（约 249 MB）。其余是编码器烘焙 11.5 MB、打包池 44.2 MB、四张图各自的 ORT 会话开销与单句工作区。把 vits 也改成打包驻留，驻留可再降约 205 MB（43.5 MB 的包对 249 MB 的 fp32），稳态有望落进 260 至 310 MB。这一项没有起头：vits 是卷积为主的图，需要给 PackedMatMul 之外再写融合反量化的卷积路径并逐层验数值，是独立一块工作，本阶段按约束只做到解码器侧。目标 300 MB 量级未完全达到，差在 vits 这一项，账如上，没有砍任何功能凑数。

### 内核现状与剩余工作

融合反量化内核是标量实现（没有 NEON intrinsics，与 A57 的 ARMv8.0 基线一致，不依赖点积与 fp16）。隔离微基准（x86，相对数）：一层解码的四个大线性层走打包 GEMV 共 3.43 ms，折合每步纯矩阵乘约 82 ms；但端到端实测每步解码 444 ms（烘焙模式 44.7 ms）。也就是说内核本身的 MAC 吞吐与 ORT 烘焙 GEMV 同档，步时的大头不在矩阵乘，而在图里其余算子（注意力、归一化、KV 状态张量逐歩传递）与自定义算子逐次分发的开销。剩余工作按收益排序：一是给 GEMV 内层做 NEON 向量化；二是减少逐歩的张量传递与算子分发次数（状态打包常驻、算子合批）。这两项都不影响数值口径。真机上的实际步时由标定包测量，x86 的相对数不外推。

## 三、aarch64/musl 移植

产物在 `host/dist-aarch64/`（tts_host、tf_check、test_softclip），构建说明同目录 BUILD.md。方法：clang 18 以 Alpine 3.24.4 aarch64 rootfs 为 sysroot 交叉编译，头文件只取 sysroot 的 musl 与 libstdc++（ORT 头用 sysroot 里 1.24.4 的），链接显式指定 aarch64 的 GNU ld；产物为动态链接 musl 的 ELF，依赖 libonnxruntime.so.1（1.24.4）、libstdc++.so.6、libgcc_s.so.1，与目标容器装系统 onnxruntime 包的形态一致。编译基线是通用 armv8-a，没开 ARMv8.0 之后才有的扩展。

与 x86 侧 ORT 1.22.1 的兼容性：四张图在 1.24.4 上加载与运行实测通过，自定义算子域 `potato::PackedMatMul` 在 1.24.4 注册与分发正常（A57 验证全程就是在 1.24.4 上跑的）；ORT 的 C++ API 用量（Env、Session、CustomOpDomain、Allocator）两版无差异点。数值上与 x86 构建的差异见下节，与 x86 内部两种模式之间的差异同档。

一个路径坑：`wo-packs/manifest.json` 里 stage 1 写入的 pack_file 是构建机的绝对路径，宿主只对相对路径拼 root。标定包与验证包里的 manifest 已改成相对路径（仓库原件未动），换机器部署时要注意这一条。

## 四、A57 正确性验证

环境：InstaBox 机器 potato-screen 上的 Alpine 3.24.4 aarch64 rootfs 加系统包 onnxruntime 1.24.4，qemu-aarch64-static 指定 `-cpu cortex-a57`（能力位与真机一致：无点积、无 fp16 算术）。同一套验证也在本地同配置 QEMU 里跑了全量。QEMU 只验正确性与指令合法性，本节不出现速度数字。

- 教师强迫（361 步全量，与阶段二同口径），现行基线（W4-plus 包，见第八节）：在 potato-screen 上复跑，一致率 323/361 = 89.47%，六行逐行数（60/68、64/68、42/48、63/72、51/58、43/47）与 x86 一致；对 x86 w4plus 烘焙 dump 的 logits 最大差 6.10352e-05，与 x86 打包跑的同项数值逐位相同，逐歩 argmax 361/361 全同。
- 历史对照（初代 W4 包，已退役）：一致率 299/361 = 82.83%，与 x86 的烘焙、打包两种模式相同；对 x86 烘焙 dump 的 logits 最大差 7.08e-05，逐歩 argmax 361/361 全同；六行逐行数（57/68、59/68、42/48、57/72、42/58、42/47）与 x86 逐行一致。这一组在两个独立的 aarch64 环境里各跑了一遍（本地 rootfs 与 potato-screen 的 rootfs-ort，后者的 onnxruntime 是在机器上现场 apk 装的），两遍的最大差逐位相同（均为 7.08401e-05），打包内核在 aarch64 上是确定性的。其前两行子集（共 136 步）在 potato-screen 上先行独立复跑过：一致 116/136，logits 最大差 5.72e-05，argmax 136/136 全同。
- deess2air 逐值对照：aarch64 二进制对样本 w4_s0_neutral1.wav 的 `--deess-file` 输出与 Python 原型参考逐值比，最大差 3.2e-05（约 1 个 int16 LSB），相关性 0.999999995，与 x86 宿主在阶段二的同项结果（3.2e-05）一致。
- 软削波单元：aarch64 版 test_softclip 对愤怒 take1 的输出与 x86 版逐字相同：drive=1.468，峰值 0.81741 到 0.62801，RMS −17.15 到 −17.15 dB，crest 15.40 到 13.11 dB。
- 端到端一句（aarch64 宿主全链路，packed 配置，potato-screen 上跑）：贪心 S0 合成完成，82 步，音频 3.25 秒，deess 与 softclip 均生效（结果 JSON 标记为 true），进程 RSS 484 MB（QEMU 进程口径，含模拟器开销，不作手机数字读）。结构量与 x86 同句样本同族：RMS −20.03 dB（x86 采样版 −19.42 dB）、峰值 0.474（软削波后）、频谱重心 3,633 Hz。token 序列各跑互不相同（机器上两次贪心跑 79 步与 82 步，x86 两次贪心跑 65 步与 76 步，分叉点在图内无种子抽样的首 token，见第七节），故不做包络逐点比，只作同族结构确认；数值口径以教师强迫为准。

音频逐值比对不成立的原因与阶段二相同：vits 图内噪声按进程随机，同图同输入两个进程的相关性也只有 0.44，所以音频只比结构量（包络相关、频谱重心、基频），token 与 logits 才是逐值口径。

## 五、输出链（现行定版）

顺序：合成 → deess2air → 裁静音 → 软削波 → 写出。

deess2air 参数按 DEESS.md 定版（交叉 5 kHz、阈值 −5 dB、斜率 2.0、封顶 10 dB，后接 11 kHz 起的高架空气架 +3 dB）。软削波是 tanh 型：驱动按整句峰值取 d = 1.2/peak，使峰值刚过拐点，处理后按原句 RMS 缩放回等响度。它排在裁静音之后作终级（2026-11-08 用户定版，此前在愤怒 take1 上被判为目前最好的结果）。

软削波的两组对照数字：

1. 单元口径（愤怒 take1 原始交付件）：drive 1.468，峰值 0.81741 到 0.62801（即 −1.75 到 −4.04 dBFS，等响度下净降 2.29 dB），RMS −17.15 到 −17.15 dB 不变，crest 15.40 到 13.11 dB。毛刺代理指标几乎不动（平坦度 0.1015 到 0.1046），它的定版依据是听感，不是代理指标。
2. 宿主链内口径（packed 模式 S0 一句的结果 JSON）：drive 1.890，峰值 0.635 到 0.475，RMS −19.77 到 −19.77 dB，crest 15.83 到 13.31 dB，结果里 deess_applied 与 softclip_applied 均为 true。

## 六、真机标定包

`phone-calib/`（约 509 MB）：aarch64 产物（bin/，含第八节的 per-graph 池修复）、为 W4-plus 重新生成的打包图与词典与 65 条参考包（host/）、GPT 的 W4-plus 包与 vits 的 E 混合包（wo-packs/，manifest 已改相对路径）、编码器与 vits 的图模板与 tf_check 输入（work/）、`run-on-phone.sh` 与 README.md。脚本按 speedtest 的风格写：幂等（每次覆盖结果文件）、结果写 `calib-result.txt`、含环境、onnxruntime 在位检查、4 句合成（S0 贪心加 S0/S1/S2 采样 seed 42，2 线程默认，出货配置 packed 加 no-arena）、逐句总耗时与音频时长与 RTF 与逐段计时（g2p、encoder、first、decode、vits、deess）与 RSS，末尾给首句延迟（boot 加首句总耗时）。包在本地已用 x86 宿主按同一 root 布局实跑验证可合成（初代包 RSS 495 MB；换 W4-plus 后复跑 504.66 MB，同档）。

真机数字（速度、RTF、驻留）要等标定在手机上跑完才有，本报告不预填。已知的手机侧前提：电池已坏、全程插墙充；4 线程满载有掉电重启前科，脚本默认 2 线程。

## 七、已知边界

- 端到端 token 序列不保证可复现：首 token 在 first_stage 图内抽样、无种子输入，贪心请求也可能在首 token 分叉（阶段二已记录；本阶段在 potato-screen 上实测到同一句两次贪心跑分别给出 79 步与 82 步两条序列）。教师强迫口径不受此影响。
- 宿主不自建 outdir：write_wav 对不存在的目录静默失败、结果 JSON 照常报成功路径。本阶段第一次端到端就栽在这里（JSON 完整、wav 没落盘，先建目录后复跑才拿到文件）。标定脚本已在跑前建好 out/，直接调宿主时要先建目录。
- 打包模式目前只覆盖 GPT 的 W4-plus 包（初代 W4 只作历史对照）；W8 仍走烘焙路径（加载冒烟在阶段二已过），与定版口径（W4-plus 为出货主配置）一致。
- 参考包仍是 65/69（缺的四条是上游 G2P 在其参考文本上崩溃，宿主回退 neutral1），本阶段未动。
- 速度：打包模式在 x86 上比烘焙慢（解码每步 444 ms 对 44.7 ms），原因是第二节所述的图内开销而非内核吞吐；这只是 x86 相对数，ARM 上的结论以真机标定为准。

## 八、GPT 包换代：W4-plus（GPTQ 加料版）

阶段三收尾后，GPT 的出货包换代为加料版 PTQ 的产物（GPTQ 误差补偿加 MSE 最优裁剪，方法与评测见 work/PTQ-PLUS.md）：`wo-packs/gpt_*_w4plus.npz`，清单 `wo-packs/manifest_w4plus.json`，烘焙图 `work/wo_graphs/w4plus/`。与初代 W4 包逐字节同体积（92,735,008 B），格式兼容（分组 64 不对称、半字节打包、fp32-residual 与 w8-fallback 的条目逐字节照抄，589 条 manifest 条目的 scheme 与 shape 零差异，已逐项核对）。

换代收益（PTQ 侧测量，本阶段复验见下）：教师强迫一致率 299/361 = 82.83% 升到 323/361 = 89.47%（逐组 60/68、64/68、42/48、63/72、51/58、43/47，初代为 57/68、59/68、42/48、57/72、42/58、42/47）；愤怒版破音尾巴的最差平坦度 0.2563 降到 0.1177，已低于 fp32 组的 0.1659，中位 0.1085 改善到 0.0967（fp32 为 0.0938）。初代包数字自此只作历史对照。

### 换代暴露的两个耦合（复验时逐个定位并处理）

1. 打包图冻结了生成时的包代。make_packed_graphs.py 只把 MatMul/Gemm 权重改成打包输入，其余条目（嵌入 Gather、残差、bias、norm）在生成时用当时的包还原成 fp32 烘进图里。直接换池里的包，打包路径会混用两代数据：实测打包对烘焙的 logits 最大差 4.11、argmax 只合 329/361、一致率掉到 315/361，定位到嵌入张量（恰是 GPTQ 改动最大的张量，还原差 6.39）。处理：用 w4plus 清单重新生成打包图（产物在 host/packed_graphs_w4plus/，初代图保留在 host/packed_graphs/ 与仓库原树保持一致）；标定包内的是新图。结论：打包图是包代产物，换包必须连图一起换。
2. 共享权重池假设两包逐字节相同。WeightPool 的描述符按张量名键入、先写者胜，初代两包相同所以无感；GPTQ 按图分别校准（first 用教师强迫激活、stage 用自回归 rollout），两包不再相同，stage 图静默用上了 first 包的张量。嵌入修复后仍差（最大差 2.82、一致率仍 315/361），定位在此。处理：宿主改 per-graph 池（WeightPool::load 增加 sections 参数，main.cpp 与 tf_check.cpp 各持两池），这是加载器的一处代码修正，包格式本身确实没变。代价是跨图去重基本失效：两池唯一字节合计 87,820,800（初代共享池 44,173,824），tf_check 打包进程 RSS 从 262 至 275 MB 升到 304.6 MB；宿主整机 RSS 无实质变化（见第二节注）。

### 复验（新基线口径：对 w4plus 烘焙图）

- x86 烘焙（tf_check 对 work/wo_graphs/w4plus/）：323/361 = 89.47%，逐组与 PTQ-PLUS 的 Python 评测逐数一致。
- x86 打包（修复后）：323/361 = 89.47%，对烘焙 dump 的 logits 最大差 6.10e-05，逐歩 argmax 361/361 全同，与初代包的等价量级相同。
- A57（potato-screen，qemu -cpu cortex-a57，ORT 1.24.4）：323/361 = 89.47%，逐行与 x86 相同；logits 最大差 6.10352e-05（与 x86 打包跑逐位相同），argmax 361/361 全同。
- 端到端：换代后的标定树本地实跑可合成（packed 加 no-arena，贪心 S0 一句 69 步、2.71 秒音频、RSS 504.66 MB，deess 与 softclip 均生效）。

### 当时的默认布局（已被第九节取代）

### 0. 本轮基线（开工前同机复测，x86、4 线程；本机负载波动大，同一时段内的对照才作数）

| 口径 | RSS | 编码 | first | 解码每步 | vits 每词 |
|---|---|---|---|---|---|

### 1. 步骤一：权重池改内容寻址共享

做法：`packed.h` 里抽出进程级 `BlobStore`，张量按内容入池（FNV-1a 哈希做桶，全量 memcmp 验过才算命中，撞哈希只会多存一份、不会给错张量）；first、stage、vits 三个池共用一个 store。描述符仍按池、按名各持一份，共享的只有字节。第八节的 bug 是按名键入、先写者胜；内容寻址下两图同名字节不同就自然不共享，对初代相同包与 W4-plus 相异包都正确，没有退回老逻辑。

验收：tf_check 打包一致率守 299/361，logits dump 与改前、与第九节存档（`host/logits_packed_x86_dedup.bin`）逐字节相同；store 唯一字节 44,173,824 B，与第二节共享池时代逐字节一致；tf_check RSS 304.66 → 276.42 MB（回到 274.9 的共享池台阶，余差为分配器噪声）；宿主 boot 后 RSS 473 → 446 MB。各段计时无变化（无数学改动）。

### 2. 步骤二：vits 打包驻留

新图 `host/packed_graphs/vits_wnfold.onnx`（1.9 MB，生成器 `host/make_packed_vits.py`）：E 包 225 个量化张量全部改写为自定义算子，权重以打包字节驻留、计算时逐块反量化，激活 fp32。其中 Conv 218 个走 `potato::PackedConv`，ConvTranspose 5 个走 `potato::PackedConvTranspose`，Gather 2 个走 `potato::PackedGather`。两个例外如实记账：`emb_rel_k/v` 共 24 张小表（fp32 共 83 KB）是 Pad 的数据输入、不是线性权重，生成图时按包内数值反量化烘焙回图（与烘焙路径加载时算出的值逐位同），没有为 83 KB 写新算子；fp32 残差（bias、范数）照旧烘焙。

内核（`host/src/vits_kernels.cpp`）：每个节点先把权重整张反量化一次进暂存，计算按输出位置分块（LT=1024），分块内是 4 通道 × 32 位置的寄存器分块；任务用原子计数器动态取活（静态分块在共享虚机上会被最慢的 worker 拖住尾巴，实测图内只有约 3 GMAC/s，动态取活后与隔离冷测同档）。x86 有 AVX2+FMA intrinsics 分块，按运行时检测分发；转置卷积按相位分解为 stride=1 卷积复用同一内核，dilation ≠ 1 落回标量 gather 实现。反量化本身全程只占 46 ms（vits_check 口径），可忽略。

数值验收（新工具 `host/src/vits_check.cpp`，固定 feed + 阶段一去噪口径，噪声 Constant 置零）：226 个输出逐层对烘焙 E 图比对，最差相关性 1.000000，最大绝对误差 2.03e-03（出在解码深层，相对 RMS ≤ 3.8e-05，是累加顺序差，不是权重差）；全图对 fp32 参考的相关性打包 0.959881、烘焙 0.959880，相对 RMS 打包 0.293292、烘焙 0.293293，E 包基线 0.9599 守住且与烘焙同档；打包对烘焙的音频最大差 3e-05 量级。

内存账：三池 store 唯一字节合计 87,123,996 B（GPT 44,173,824 + vits 42,950,172），vits 的 249 MB fp32 注入就此取消。宿主稳态 RSS：打包 no-arena 544–573 → 270–318 MB（热身后 318 MB），打包 arena 版 407–430 MB。tf_check 不加载 vits，不受本步影响。

### 3. 速度账（守线结果：GPT 段变快，vits 段没守住，待裁决）

先说变快的：本步期间查出 ORT 线程与内核池抢核是打包模式的一大损耗（ORT intra 线程空转与池的 4 个 worker 挤 4 个 vCPU）。打包会话的 ORT 线程数改为默认 1（新开关 `--ort-threads`，只影响打包会话；线程数不改变这些算子的数值结果）。单这一项：GPT 解码 157–196 → 43–46 ms/步（追平烘焙带 46–57），first 6.6–8.0 s → 2.3–4.1 s，vits（vits_check 口径）22.4 → 10.7 s。

vits 段的交换数：宿主 vits 43–59 → 128–147 ms/词，约 2.5–2.9 倍；vits_check 口径 75 词打包 11.0–11.3 s 对烘焙 4.7 s，约 2.4 倍。账要算清：图内卷积总量按逐节点 MAC 实数是 139.7 GMAC（先前用 shape 推断估的 28 GMAC 只覆盖了一部分节点，是错数，不再引用）；烘焙路径在图内约 40 GMAC/s，那是 ORT MLAS 在本机（EPYC）用 AVX-512 跑的；打包内核在本机约 13 GMAC/s，与隔离冷测同档，没有图内损耗，差的是 AVX2 对 AVX-512 的位宽与 MLAS 的分块效率。已做过的补救按顺序：标量版 64.6 s → 窗口式 gather → AVX2 寄存器分块 → 动态取活 → ORT 线程修正，合计压到 11 s 档。再往上只剩两条路，都不在本轮授权内：一是给这台开发机写 AVX-512 分块（目标设备没有 AVX-512，属对着开发机过拟合，且追加约束明说只留分发点、不做专项优化）；二是给真机写 NEON 分块（aarch64 现在走通用分块，clang -O2 自动向量化寥寥，实测 vits_kernels 目标文件里 fmla 仅 4 条）。目标侧的结构不同：A57 上烘焙走 MLAS 的 NEON、打包走通用分块，两边同为 4 宽向量，x86 上这条 2 倍位宽差在真机不存在；但真机 RTF 至今未标定，差距到底多大只能等标定回传。

按第三步守线口径，本步不算验收通过，交换数报用户裁决（见本节七）。裁决前代码维持现状：`--packed` 默认含 vits 打包，`--vits-baked` 一键切回（GPT 打包、vits 烘焙），翻默认只是改一个分支条件。

### 4. 烘焙路径保留（追加要求一）

- 开关就是现行机制：不带 `--packed` 即全烘焙（加载时还原 fp32 注入、ORT 原生图、无融合反量化内核）；`--packed --vits-baked` 是混合档，只作归因。烘焙读的旧包组文件（仓库原样那套与标定包的 `fallback-gen1/`）本轮未动；去重共享包只供打包路，两条路入口分清。
- 每步复验都带烘焙：tf_check 烘焙全量 299/361、RSS 1277.68 MB（基线约 1250 MB，同档）；宿主烘焙冒烟 4 句 RSS 1830 MB、各段计时与基线同带。
- 定位：打包 = 省内存，给手机与内存紧的机器；烘焙 = 省算力，给内存宽裕的机器（桌面、骁龙 855 以上）。

### 5. 可移植性（追加要求二）

- 分发：`host/src/cpu.h` 做运行时检测并在启动日志打印。aarch64 用 getauxval：HWCAP 的 ASIMD（NEON 基线）、ASIMDHP（fp16）、ASIMDDP（SDOT），HWCAP2 的 I8MM。x86 用 CPUID + XCR0：AVX2、FMA；AVX-512 只检测记日志，任何内核不许依赖。通用实现是地板，特性缺失自动落回；构建仍是通用 armv8-a / 通用 x86-64，没有编译期写死单一路径。权重包格式与 manifest 未引入任何只对现机成立的字段或对齐假设。
- 目标设备集与路径定位：

| 设备 | 路径定位 |
|---|---|
| 小米 4c（骁龙 808，ARMv8.0 无点积） | 打包 + 通用基线（现行；NEON 分块待裁决） |
| 骁龙 430 | 与现机同档：打包 + 通用基线，单核更弱，内存账照现行 |
| 骁龙 855 起 | SDOT 与 fp16 可用，int8 计算从负收益转可选速度项（分发点已留，未实现）；也可直接烘焙 |
| 骁龙 8 Gen 3、天玑 9300 | 内存宽裕，直接烘焙 |
| 桌面 x86-64 | AVX2 是基线档（本轮内核即此档）；内存宽裕烘焙，内存紧打包 + AVX2 内核 |
